# 解包 UNPACKED — 每日寫稿指南

每天清晨的排程（Claude 排程任務「解包：每日寫稿」，台灣時間 05:23）照這份做：**收點播台 → 選 2～3 款遊戲（點播優先）→ 研究 → 寫深度專題＋粉專稿 → 獨立查核 → 回答點播台的問題 → 上架**。
讀者只有一個人：痞子葳（台灣、PC 玩家、經營遊戲頻道「遊戲狂想曲」和它的粉專）。他要的是「比新聞更深、看完就能決定要不要玩、還能拿去發文拍片」的專題。
所有內容一律**繁體中文、台灣用語**；回報時稱呼他「痞子葳」。

## 1. 選題

- 每天 **2～3 款**。素材不夠好、查不到足夠來源，寧可只寫 2 款。
- **點播優先**：點播台有待寫的點播，先寫點播（照 `QA_GUIDE.md` 第 3 節，`kind_label` 前面加「點播・」），剩下的名額再照下面的規則選。
- 今天（台灣日期）已經有專題的話（例如 App 上線當天，或痞子葳在對話裡先請 Claude 寫了一篇），新的 `rank` 接著往下編、不要重複；今天已經有 3 篇以上，這次就只寫 2 篇。
- **全收**：大作、獨立遊戲、免費遊戲、平台獨佔（PS5、Xbox、Switch 2、Netflix 的電視／電腦遊戲都算）、即將上市、大型更新。
- **一律排除**：
  - 只在手機上架、或以手機為主的遊戲。
  - 抽卡、付費解鎖角色或內容為核心的遊戲（不管在哪個平台）。痞子葳不喜歡「什麼都得課金才能解鎖」。
  - 免費但只賣外觀、或內購內容還不明的 PC／主機遊戲**可以寫**，課金雷達要講清楚。
- **組合**：盡量一款大作或熱門話題（同上暴增、上市倒數、評測解禁）＋一款黑馬／獨立／新奇玩法＋一款即將推出或有大更新的。三款不要同類型。
- **熱度來源**：candidates.json 之外，用 WebSearch 查當天的遊戲新聞（發表會、評測解禁、主機獨佔、Switch 2、Netflix、Game Pass／PS Plus、限時免費、延期、爭議）。台灣媒體（4Gamers、巴哈新聞、遊戲角落）和國外媒體都要看。
- **不重複**：寫過的不再寫。除非有重大變化（正式版、上市後評測、改版、爭議）→ 寫追蹤篇，id 加 `-2`（例：`rob-run-2`），開頭交代「上次解包之後發生了什麼」。
- 不要只因為是台灣民俗、宮廟題材就選；照熱度和品質選。
- **痞子葳願望單上的遊戲**（`wish.json`、候選裡的 `mine: true`）：每一款都會由另一個排程「願望單解包」（`WISH_GUIDE.md`）寫一篇附買不買判定的解包（`kind: wish`），所以這裡**不要搶著寫**還在排隊的。已經有願望單解包的，碰到正式上市、評測解禁、大型更新這種重大變化，照「不重複」的規則寫 `-2` 追蹤篇，並在追蹤篇裡附新的 `buy`（買不買）。
- 願望單解包也是專題（`kind: wish`、`rank` 從 20 開始），「最近 7 天舊稿」要順手更正的範圍包括它們。

## 2. 研究（每款至少 8 個來源）

一定要查到、而且每一條都附來源的：
- 開發／發行、上市日（或搶先體驗日）、平台。
- **台灣售價**：Steam 台灣區、PlayStation Store 台灣、Xbox 台灣、Nintendo eShop 台灣；免費就寫免費＋內購狀況。
- **中文**：介面、字幕、語音分開講；繁中還是只有簡中。
- **台灣能不能玩**：區域限制、伺服器地區、平台在台灣有沒有開放。
- 反作弊、強制連線、DRM、帳號綁定。
- **內購賣什麼**（外觀、季票、加速、抽卡），以及開發商過去的收費紀錄。
- 系統需求、遊玩時數、媒體評分、Steam 評價、玩家主要誇和罵什麼、爭議。
- 官方預告的 YouTube id。

來源優先順序：官方商店頁、官方公告／說明中心、發行商新聞稿 > 主要媒體 > 整理站。論壇與整理站只能當輔助，不能是唯一來源。查不到的寫進 `pending`，**不要猜、不要自己推估數字**。

查資料的訣竅：
- 雲端環境的指令列連不到 Steam；Steam 商店頁要先用 WebSearch 找到網址，再用 WebFetch 打開（自己拼的網址可能被擋）。`candidates.json` 裡已經有候選的台灣價格、評價、標籤和繁簡中文支援，可以先拿來篩。
- 要有效率：先列出這款要查的清單，能一起送的搜尋一次送出；一件事找到一手來源就夠，不用再找第二個說法一樣的。
- Steam 的同上、價格、評價、截圖、預告不用自己抄：推上去以後 Actions 會自動補進 App。專題裡寫到人數或評價時，寫當下查到的數字並附來源。

## 3. 寫專題（`apps/unpacked/data/features/<id>.json`）

`id` 用遊戲英文名的小寫連字號（`gta-vi`、`rob-run`）。檔名＝id。欄位照範例，重點：

| 欄位 | 要求 |
|---|---|
| `date` | 今天（台灣時間），`rank` 是今天的排序（1 放最重要的；今天已經有專題就接著往下編） |
| `kind` | `new` 新作、`ea` 搶先體驗、`upcoming` 即將推出、`update` 大型更新、`exclusive` 平台獨佔、`hot` 熱門話題、`indie` 獨立黑馬、`free` 限時免費、`classic` 經典回顧；`kind_label` 是顯示的字 |
| `game` | `zh` 用台灣官方中文名，沒有就用原名並在 `zh_note` 寫「暫無官方中文名」；`steam` 填 appid（沒有就 null）；`price_text` 先寫最重要的那個價格（App 會取「／」前面那段當標籤） |
| `headline` | 一句話定位，12～40 字 |
| `hook` | 第二人稱的情境開場，50～150 字，用遊戲最有畫面的一瞬間 |
| `verdict` | `stamp` 只能是「推薦／觀望／不推薦」；`label` 是具體建議（現在就玩、免費先試、等特價、等評測、有主機就衝、等台灣開放、跳過…）；`summary` 2～3 句講清楚為什麼；`for`、`against` 各 3 條，要具體到「什麼樣的人」 |
| `facts` | 10～15 條，每條 `s` 是來源編號陣列；還沒證實的加 `"p": true` |
| `money` | `level`：0 無內購、1 買斷＋可選內購、2 季票／通行證、3 付費加速或資源、4 抽卡／付費變強；不知道就 `null`。`notes` 寫他會關心的事，`flags` 放短標籤 |
| `zh`、`tw` | 中文與台灣能不能玩（`tw.ok`：true／false／"partial"） |
| `rig` | 「你的 SCAR 18」：拿他的筆電對照官方需求（見下） |
| `time` | 遊玩時間或一輪多久 |
| `media.yt` | 官方預告 YouTube id（11 碼），先找官方或發行商頻道，找不到才用 IGN／GameSpot 轉載；用 WebSearch 限定 youtube.com 確認 id。可以放 2～3 支（上市預告、玩法預告…），App 會從每支預告各抓 3 張畫面進相簿。`title` 寫中文、說清楚是哪一支（例：「上市預告」「實機玩法 12 分鐘」），短影音牆會直接顯示；非 Steam 遊戲短影音只能播這些，至少放 2 支 |
| `media.images` | **非 Steam 遊戲必放** 4～8 張官方截圖或主視覺（PlayStation／Xbox／Nintendo 商店頁、官方網站、Netflix Tudum、發行商新聞稿裡能直接連結的 https 圖片；用 WebFetch 打開官方頁、請它列出圖片網址）。第一張當主視覺，最好是橫的主視覺圖。Steam 遊戲可以不放（會自動用 Steam 截圖和動態預告） |
| `watch` | 接下來要盯的 2～3 件事（追蹤牆會用） |
| `sections.gameplay` | `loop` 4～6 步核心循環；`body` 3～4 段，講「你在遊戲裡實際會做什麼」 |
| `sections.hour` | 「你的第一個小時」3～5 步，實用（設定、選什麼、先做什麼、要避開什麼）。沒玩過就寫「照官方說明和玩家整理」 |
| `sections.compare` | 2～4 款相似作 `{name, same, diff, steam?}`：像在哪、差在哪。那款在 Steam 上就填 `steam`（appid 數字），App 點卡片會打開它的情報卡（介紹、截圖、評價）；沒填的由資料管線照名字去 Steam 對，對不到就只給點播、問 Claude |
| `sections.story` | `safe` 不劇透的設定與開場；`spoiler` 只放已上市、有來源的劇透，沒有就空陣列；完全沒劇情的遊戲整個設 null |
| `sections.studio` | 幕後：誰做的、前作、開發過程、商業模式、爭議 |
| `sections.voices` | 誇、罵各 2～4 條（媒體與玩家的共識，不捏造引言），`debate` 是吵最兇的 1～2 點 |
| `sections.timeline` | 3～9 個時間點，未來的也可以放 |
| `sections.discuss` | 3～4 題「值得聊的」，要有觀點、能拿去拍影片或發文討論 |
| `sources` | 每個 `{t 標題, u 網址, d 日期}`，至少 8 個 |
| `pending` | 還沒查證、先不當真的事 |

**「你的 SCAR 18」**：痞子葳的筆電是 ASUS ROG Strix SCAR 18（G835）：Core Ultra 9 275HX、RTX 5090 Laptop（24GB VRAM）、64GB DDR5、2TB SSD（大約剩 800GB），可以接 4K 大電視。照官方需求判斷（`verdict` 例：綽綽有餘、開滿沒問題、首發用不上、不吃硬體）；有 DLSS／FSR／光追支援才寫（要有來源）；容量超過 100GB 要提醒；主機獨佔就直說首發用不上；雲端串流就說不吃硬體。

**寫作規範**
- 像懂遊戲的朋友在講：具體、有畫面、有判斷。不准農場用語（史上最強、神作降臨、不玩後悔、震驚）。
- 台灣用語：伺服器、影片、軟體、搶先體驗、更新檔、品質、預告片、硬碟。不准出現簡體字。
- **不抄來源原文**：全部用自己的話重寫；真的要引用，一篇最多一句、15 字以內。
- 每個數字、日期、價格都要能在 `sources` 找到；不確定就 `"p": true` 或放進 `pending`。

## 4. 粉專稿（`fanpage`，遊戲狂想曲用）

- `post`：220～450 字。結構：**情境開場**（第二人稱 1～2 句）→ **一句話定位**（誰做的、什麼類型、何時在哪上）→ **玩法**（你會做什麼）→ **查證過的硬資訊**（平台、價格、中文、台灣能不能玩、同上或評價）→ **結尾二選一提問**。段落之間空一行。
  - 不能放 `pending` 裡的事；不能和任何來源（包括其他粉專，例如 TGP 玩家口袋）的句子相像，開場也不能套用別人的句型。
- `titles`：剛好 3 個，各 ≤ 28 字：一個資訊型、一個好奇型、一個話題型。
- `card`（App 會畫成塗鴉圖卡）：`kicker` ≤ 16 字（例：社群熱議｜Steam 同上近 20 萬）、`title` 兩行用 `\n` 分開、每行 ≤ 11 字、`sub` ≤ 20 字、`tags` 3 個各 ≤ 6 字、`points` 3 條（`h` ≤ 8 字、`t` ≤ 22 字）。想指定圖卡用哪張圖就填 `card.image`（要能直接連結的 https 圖片）。
- `tags`：4～6 個 hashtag，最後一個固定 `#遊戲狂想曲`。
- `script`：60 秒口播稿，口語、230～300 字，第一句就是鉤子，結尾丟問題。
- `credit`：素材來源（例：圖片／影片來源：Kefir 官方 Steam 商店頁與預告）。
- `threads`：`{post, topic}`，Threads 版（粉專作戰台發 Threads 時用；沒寫的話 App 會直接用 `post`）。`post` 120～300 字，比上面那篇更短、更口語：一句鉤子＋最有感的一兩個硬資訊＋結尾提問（Threads 一則上限 500 字）；內文**不放 #**。`topic` 是 Threads 那一個主題標籤，不含 #（例：Steam、獨立遊戲、恐怖遊戲）。
- 所有粉專文字都**不放網址**（各平台的連結規則不一樣，粉專作戰台發文時會自己加），也**不出現「痞子葳」**（粉專只用「遊戲狂想曲」）。publish.py 會擋。

## 5. 獨立查核（一定要做）

寫完以後，用 Agent 工具開一個**沒看過寫作過程**的子代理，只給它專題 JSON 的路徑，請它：
1. 逐條打開 `facts` 的來源網址，確認每一條都被來源支持（日期、價格、平台、人數、語言、地區、分級）。
2. 檢查 `fanpage.post`、`card`、`script` 裡的每個硬資訊，都能對應到某條已證實的 fact。
3. 回報不被支持或寫錯的地方。

照它的回報修：錯的改掉；查不到的改成 `"p": true` 或移到 `pending`，並從貼文、圖卡、口播稿拿掉。

**順手更正舊稿**：今天查新聞時如果發現最近 7 天解包過的遊戲有重大變化（延期、改價、正式上市、伺服器關閉、平台改變），把那篇的 `facts`、時間軸和粉專稿（貼文、圖卡、口播稿）一起改對，`sources` 補上新來源，`updated` 改成現在時間；變化大到值得再講一次，就照第 1 節寫 `-2` 追蹤篇。沒有就不用動。

**順手更新活動表**（`apps/unpacked/data/events.json`，App 的大特賣倒數和出擊日曆用）：查新聞時看到 Steam 公布或更改特賣、新品節、主題節的日期（例如黑色星期五特賣、2027 下半年的時程），或 TGA 這類頒獎典禮改時間，就照官方公告更新。只收**官方來源**（Steamworks 活動時程 https://partner.steamgames.com/doc/marketing/upcoming_events 、Steam 官方公告、活動官網），`src` 附上。時間一律寫 UTC：Steam 慣例是太平洋時間上午 10 點，冬令時間（11 月第一個週日到 3 月第二個週日）是 `T18:00:00Z`、夏令時間是 `T17:00:00Z`；官方有寫確切時間就照官方。`kind`：`sale` 大特賣、`fest` 新品節與主題節（新品節加 `"big": true`）、`show` 頒獎或發表會、`vote` 投票截止。結束超過 30 天的可以刪。

## 5b. 舊稿回訪（每天 1～2 篇，不算在當天的篇數裡）

App 的每篇專題都有「寫稿之後」：GitHub Actions 每小時比對 Steam，記下寫稿之後的變化（加了繁中、上市、正式版、改免費、原價調整、好評率大轉向、開放工作坊），也收官方公告。變化大的舊稿，App 會在文章上方貼「寫稿之後有變」——內文已經不是現在的樣子了。這一節把它改回現在的樣子。

1. 列出候選（只讀、不改檔）：`python3 _build/apps/unpacked/tools/revisit.py --kind f`。它只列寫稿超過 7 天（7 天內照第 5 節「順手更正舊稿」直接改）、而且有真的變化，或 60 天以上沒對過資料又累積 3 則以上官方更新的。沒有候選就跳過這一節。
2. 挑分數最高的 1～2 篇。點播和今天的新專題優先，時間不夠寧可只回訪 1 篇。同一款今天要寫 `-2` 追蹤篇的（第 1 節「不重複」），舊稿照第 4 步改硬資訊就好，`rev` 寫「已寫追蹤篇：…」。
3. 研究：清單列的官方公告點進去看全文，加上 Steam 商店頁，再查 2～3 個可靠來源（評測、媒體報導）。只改**真的變了**的地方，沒變的一個字都不要動。
4. 改寫 `apps/unpacked/data/features/<id>.json`：
   - `facts` 改對，新來源加在 `sources` **最後面**（舊的不要刪，編號才不會亂）。
   - 跟著變的段落一起改：中文（`zh`）、台灣（`tw`）、課金（`money`）、`timeline` 補上新的里程碑、`watch` 換成現在要盯的。
   - 結論要不要改判：例如當初「先觀望」是因為沒中文、還在搶先體驗，現在都解決了、評價也好，就改「推薦」，`verdict.summary` 講清楚為什麼改。改判一定要寫進 `rev`（例：「觀望→推薦：加了繁中、推出正式版」）。願望單解包的 `buy` 照新價格、新評價重新判斷。
   - **粉專稿（`fanpage`）不要改**：那是當時發出去的貼文。
   - `updated` 改成現在時間（`YYYY-MM-DDTHH:MM:SS+08:00`），`rev` 最後面加一筆 `{"d": "今天的日期", "t": "4～60 字講改了什麼"}`（例：「加了繁中、推出正式版，中文段和結論已更新」）。App 會在文章上方和「寫稿之後」顯示這一筆；`publish.py` 會擋 `updated` 沒跟著改的。
5. 改過的地方一樣要過第 5 節的獨立查核（只查改過的部分）。

## 7. 回報

最後用繁體中文、短短幾行回報給痞子葳（排程時用 PushNotification 推播到他手機）：第一句當標題「今天解包：A、B、C」，後面各一句為什麼值得看；有待確認的事、改了哪篇舊稿各一句帶過。不用列步驟、不寫技術細節。沒推上去就照實說原因。

**願望單特價快報**（推播的最後一段；`wish.json` 的 `state` 是 `ok` 才做）：
- **到價**優先：`index.json` 裡有 `buy.target` 的專題（大多是願望單解包），現價（`live.json` 的 `price.final`，沒有就看 `wish.json` 的 `p[0]`）小於等於 `buy.target`、而且 `buy.call` 不是「別買」，就寫「A 到價（目標 NT$300，現在 NT$279）」。
- 再看願望單上正在特價的遊戲（`p[2]` > 0），挑出符合任一條的：
- **新特價**：`sale.from` 在 24 小時內。
- **史低**：現價 `p[0]` 小於等於追蹤以來最低 `low[0]`，而且追蹤滿 14 天（`low[2]` 是開始追蹤的日期）。追蹤不滿 14 天不准說「史低」。
- **快結束**：`sale.end` 在 24 小時內。
- **限時免費**：`p[2]` 是 100。

有的話，在推播最後加一段「｜願望單：A 到價、B -50%（史低）、C -30%（明天結束）」，到價的全部點名，特價的最多點名 2 款，其他寫「等 N 款」；遊戲名用台灣官方中文名（沒有就用英文）。整則推播控制在 250 字以內。沒有就不寫這段。痞子葳在 App 裡標的「想玩」只存在他手機，推播看不到，不用管。

**點播台**：照 `QA_GUIDE.md` 第 6 節加一段（例：「｜點播台：《A》寫好了、回了 3 題」）。

**舊稿回訪**：有回訪就加一段「｜舊稿回訪：A（加了繁中）、B（觀望→推薦）」，括號裡一句話講最重要的變化。
